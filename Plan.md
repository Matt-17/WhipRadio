# Local Llama Radio — Phase 1 Implementation Plan (MVP)

> **Audience:** AI coding agent (Claude Fable 5). Execute milestones strictly in order.
> Every milestone ends with **Acceptance Criteria** — do not proceed until they pass.
> Starting point: **an empty folder**. Target OS for runtime: Linux containers (dev host may be Windows 10 + VS 2022 + Docker Desktop).

---

## 1. Goal

A fully local, AI-driven internet radio station orchestrated with **.NET Aspire**:

- Continuous audio stream (Icecast, MP3) playable in **Winamp/VLC AND in the built-in web app** via HTML5 `<audio>`.
- **Locally generated music** (two backends: instrumental via MusicGen, vocal via ACE-Step) stored in a persistent "record collection" (SQLite + audio files).
- **Announcements** between songs: generated by a local LLM (Gemma via Ollama) in a **two-stage pipeline**:
  1. *ScriptWriter LLM call* — produces the announcement content (song intro, joke, weather report, banter).
  2. *VoiceDirector LLM call* — rewrites the script in the **current moderator's persona**, injecting speech markers (`[pause:400ms]`, `[breath]`, `[rate:slow]`, filler words like "äh", "hm").
- **TTS** behind an `ITtsEngine` interface (default backend: Kokoro sidecar; swappable).
- **Multiple moderators** stored in the database, each with persona prompt, voice id, language, speech style, and music taste (incl. vocal/instrumental preference).
- **Weather announcements** via an `IAnnouncementDataSource` abstraction (Open-Meteo implementation, no API key).
- Simple **Blazor web app**: live player, now playing, vote up/down, moderator list, track library, play log, basic settings.
- **Playout model: strictly sequential** — Song → Announcement → Song → Announcement (no crossfade in Phase 1).
- **GitHub Action** (manual `workflow_dispatch` only) that builds and pushes all Docker images to GHCR.
- Unit tests (xUnit) and a green `dotnet build` / `dotnet test` at every milestone.

### Non-goals (Phase 2+) — do NOT implement
- Crossfading, ducking, top-of-the-hour precision timing
- AI program director / format planning
- Greetings/requests via web app
- Advertising
- News & traffic sources (only the interface is prepared)

## 2. Architecture

```
+--------------------------------------------------------------------------+
| .NET Aspire AppHost                                                      |
|                                                                          |
|  +----------------+   +--------------+   +--------------+               |
|  | Orchestrator   |-->| Ollama       |   | tts-sidecar  |               |
|  | (.NET Worker)  |   | (gemma3)     |   | (Py/FastAPI, |               |
|  |  - ShowRunner  |-->|              |   |  Kokoro)     |               |
|  |  - MusicProd   |   +--------------+   +--------------+               |
|  |  - AnnounceProd|                                                      |
|  |  - Playout     |-->+--------------+   +--------------+               |
|  +-------+--------+   | music-sidecar|   | Icecast      |<== ffmpeg push |
|          |            | (Py/FastAPI, |   | :8000/radio  |               |
|          v            | MusicGen +   |   +------+-------+               |
|  +----------------+   | ACE-Step)    |          |                       |
|  | SQLite (volume)|   +--------------+          v                       |
|  +----------------+                      Winamp / VLC / Browser         |
|          ^                                                              |
|  +-------+--------+                                                     |
|  | Web (Blazor)   |---- <audio src="http://host:8000/radio.mp3">        |
|  +----------------+                                                     |
+--------------------------------------------------------------------------+
```

**Audio pipeline (Phase 1, gapless-sequential):**
The Playout service runs ONE long-lived ffmpeg process:
`ffmpeg -f s16le -ar 44100 -ac 2 -i pipe:0 -c:a libmp3lame -b:a 192k -content_type audio/mpeg -f mp3 icecast://source:PASSWORD@icecast:8000/radio.mp3`
For each playlist item (track WAV or announcement WAV) it spawns a short-lived decoder
(`ffmpeg -i item.wav -f s16le -ar 44100 -ac 2 pipe:1`) and copies its stdout into the encoder's stdin. Result: a CD-like continuous stream with no gaps and no NAudio (Linux-safe).

## 6. Core Interfaces (define in `LlamaRadio.Core/Abstractions`)

```csharp
public interface ITextGenerationService          // wraps Ollama /api/chat
{
    Task<string> CompleteAsync(string systemPrompt, string userPrompt, CancellationToken ct);
}

public interface IScriptWriter                   // stage 1
{
    Task<string> WriteAsync(AnnouncementRequest request, CancellationToken ct);
}

public interface IVoiceDirector                  // stage 2 (persona + speech markers)
{
    Task<string> DirectAsync(string script, Moderator moderator, CancellationToken ct);
}

public interface ITtsEngine
{
    Task<TtsResult> SynthesizeAsync(string markedUpText, TtsVoiceOptions options, CancellationToken ct);
    Task<IReadOnlyList<TtsVoice>> GetVoicesAsync(CancellationToken ct);
}
// TtsResult { byte[] WavData, double DurationSeconds }
// TtsVoiceOptions { string VoiceId, string Language, double Rate }

public interface IMusicGenerator
{
    Task<MusicResult> GenerateAsync(MusicRequest request, CancellationToken ct);
    Task<bool> IsBackendAvailableAsync(string backend, CancellationToken ct);
}
// MusicRequest { string Prompt, string Genre, bool WantVocals, string? Lyrics, int DurationSeconds }
// MusicResult { byte[] WavData, string BackendUsed }

public interface IAnnouncementDataSource         // weather now, news/traffic later
{
    string Kind { get; }                         // "weather"
    Task<string> GetSummaryAsync(string language, CancellationToken ct);  // plain text facts
}

public interface ITrackSelector
{
    Task<Track?> PickNextAsync(ScheduleSlot slot, Moderator moderator, CancellationToken ct);
}

public interface IPlayoutQueue                   // thread-safe FIFO consumed by PlayoutService
{
    void Enqueue(PlayoutItem item);
    Task<PlayoutItem> DequeueAsync(CancellationToken ct);
    int Count { get; }
}
```

**Track selection weighting (implement + unit test, pure function):**
`weight = max(0.1, 1 + 0.5*UpVotes - 0.7*DownVotes) * (1 / (1 + PlayCount * 0.15))`
Filter: matching `slot.Genre` (fallback: any genre if none match), respect `moderator.PrefersVocals` when set, exclude `IsRetired`, exclude the last 3 played tracks. Weighted-random pick over remaining candidates. Retire rule: `DownVotes >= 5 && DownVotes > 2 * UpVotes`.

**Speech-marker contract** (consumed by the TTS sidecar; implement parser/normalizer in Core, unit-tested):
`[pause:NNNms]`, `[breath]`, `[rate:slow|normal|fast]` (sets segment rate), plain filler words stay literal text. Normalizer rules: strip unknown bracket tags, clamp pause to 100–1500 ms, collapse duplicate breath markers.

## 7. Sidecar API Contracts

### 7.1 TTS sidecar (`sidecars/tts`, port 8001)

```
GET  /health           -> {"status":"ok","engine":"kokoro"}
GET  /voices           -> [{"id":"af_heart","language":"en","gender":"f"}, ...]
POST /synthesize
  body: { "text": "...with [pause:400ms] markers...", "voice": "af_heart",
          "language": "en", "rate": 1.0 }
  resp: audio/wav (44.1 kHz, 16-bit, mono is fine; orchestrator upmixes)
```
Implementation notes:
- Split text on markers; synthesize segments with Kokoro; insert silence for `[pause]`;
  for `[breath]` mix in a short bundled breath sample (`assets/breath.wav`, ship a 300 ms generated/sox-made noise sample — do NOT download copyrighted audio).
- Concatenate segments with `pydub` or raw numpy; return single WAV.
- Engine module behind a small `EngineBase` class so XTTS can be added later.

### 7.2 Music sidecar (`sidecars/music`, port 8002)

```
GET  /health    -> {"status":"ok","backends":{"musicgen":true,"ace-step":false}}
POST /generate
  body: { "prompt": "energetic indie rock, driving drums",
          "backend": "musicgen" | "ace-step",
          "duration_seconds": 90,
          "lyrics": null | "..." }
  resp: audio/wav   (long-running: set generous client timeout, 30 min)
```
Implementation notes:
- MusicGen: `audiocraft`, model `facebook/musicgen-small` by default (env `MUSICGEN_MODEL`), CPU fallback works.
- ACE-Step: wrap only if `ENABLE_ACESTEP=1`; otherwise `/generate` with `backend=ace-step` returns 503 and `/health` reports it false. Orchestrator must handle 503 by generating instrumental instead and logging a warning.
- Synchronous request/response is acceptable for Phase 1 (the orchestrator calls it from a background producer; nothing blocks the stream).

## 8. LLM Prompts (store as embedded resources or `Prompts/*.txt` in Orchestrator)

### ScriptWriter system prompt (stage 1)
```
You are the script department of a small radio station called "{StationName}".
Write SHORT spoken-radio copy in language: {Language}. 2–5 sentences. No markdown,
no stage directions, no quotation marks. Output ONLY the words to be spoken.
```
User prompt is assembled per Kind, e.g. SongIntro:
```
Write an intro for the next song. Title: "{Title}". Genre: {Genre}. Vibe: {Style}.
Optionally include ONE light remark or joke. Do not invent a band name.
```
Weather:
```
Turn these raw weather facts into a casual radio weather report: {WeatherFacts}
```

### VoiceDirector system prompt (stage 2)
```
You adapt radio scripts to a specific host persona and add speech markers.
Persona: {PersonaPrompt}. Speaking style: {Style}.
Allowed markers: [pause:NNNms] (100-1500), [breath], [rate:slow], [rate:normal], [rate:fast].
Add natural filler words fitting the language ("äh", "hm" for German; "uh", "y'know" for English)
sparingly. Keep the meaning. Output ONLY the adapted text with markers.
```

### M6 — Orchestrator pipelines
Implement as `BackgroundService`s in `LlamaRadio.Orchestrator`:

1. **`MusicProductionService`** — loop: read `StationSettings.TargetQueueLength`; count non-retired tracks not yet played in current rotation… simpler Phase-1 rule: if `unplayed tracks in library < TargetQueueLength` → produce one track:
   - Pick genre from the CURRENT `ScheduleSlot` (by hour, station local time).
   - Decide vocals: if active moderator `PrefersVocals == true` AND ace-step backend available → vocal track: stage-1 LLM call to write short lyrics (add `LyricsWriter` prompt: 8–12 lines, language of station) then `/generate backend=ace-step`. Else instrumental via musicgen.
   - LLM invents `Title` (one short call: "Invent a {genre} song title, output only the title").
   - Save WAV to `/data/library/tracks/{id}.wav`, probe duration (run `ffprobe -v quiet -show_entries format=duration -of csv=p=0`), insert `Track` row.
   - Backoff 30 s between checks; serialize generations (only one in flight).
2. **`AnnouncementProductionService`** — keeps a small pool: for the next planned track (peek of selector under the upcoming slot), produce a `SongIntro`; every 4th announcement cycle produce a `Weather` announcement instead (uses `IAnnouncementDataSource` "weather"). Pipeline per announcement:
   ScriptWriter → VoiceDirector(current moderator) → `SpeechMarkerNormalizer` → `ITtsEngine.Synthesize` (voice/rate/language from moderator) → save WAV under `/data/library/announcements/`, insert `Announcement` row.
3. **`ShowRunnerService`** — the conductor. Loop:
   - Determine current `ScheduleSlot` + its `Moderator` (slot drives the active moderator).
   - `PickNextAsync` track; ensure/await its `SongIntro` announcement (generate synchronously if pool empty — with a 60 s LLM/TTS budget; on failure, skip announcement, log).
   - Enqueue Announcement then Track into `IPlayoutQueue`; write `PlayLogEntry` rows when the PlayoutService reports an item started (use a callback/channel); increment `Track.PlayCount`.
   - If queue already holds ≥2 items, wait.
   - If NO track is available at all (cold start): enqueue a station-id/banter announcement ("we're warming up the studio…") generated on the fly, then retry. This covers the "talk until music exists" requirement.
4. **`PlayoutService`** — owns the ffmpeg encoder process (§2 pipeline). On crash of ffmpeg: log, restart, continue with next item. Item playback: spawn decoder ffmpeg, `CopyToAsync` decoder stdout → encoder stdin, await exit. Publish "now playing" via an injected `INowPlayingState` singleton (current item, started at, moderator).
5. Config binding (`appsettings.json` + env): Icecast host/port/password/mount, bitrate (192k), data root.
6. Tests: ShowRunner decision logic extracted into a testable `ShowPlanner` class (given library state + slot ⇒ next actions) — ≥6 tests. PlayoutQueue FIFO + cancellation test.

**Accept:** with all containers up, within a few minutes the Icecast status page (`http://localhost:8000`) shows the `/radio.mp3` mount active; VLC can play `http://localhost:8000/radio.mp3`; you hear announcement(s) and, once generation finishes, music; `PlayLog` rows appear in SQLite.

### M7 — Web app
Pages (Blazor Server, minimal styling, one shared layout, dark-ish "radio" look but keep CSS small):
1. **/ (Player)** — `<audio controls autoplay src="@StreamPublicUrl">`; Now Playing card (poll Orchestrator's small internal API every 5 s — add a minimal API endpoint in Orchestrator `GET /api/nowplaying` and `POST /api/votes` `GET /api/library` `GET /api/playlog` `GET /api/moderators`; Web talks to Orchestrator via service discovery); vote 👍/👎 buttons for the currently playing track (disabled for announcements).
2. **/library** — table of tracks: title, genre, vocals, duration, plays, votes, created; sortable by plays/votes (server-side simple).
3. **/playlog** — last 100 entries.
